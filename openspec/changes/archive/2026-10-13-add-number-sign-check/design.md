## Context

動機は proposal.md の Why を参照。現在は単一の `number_check.py` が `int(input(...))` を `try` 内で実行し、`ValueError` を処理した後、`else` 内で各判定を表示している。既存仕様の出力順序と、新しい分岐の配置を実装前に確定するため本設計を残す。

## Goals / Non-Goals

**Goals:**
- 整数変換成功時にだけ、3通りのうち1つを必ず表示する構造にする。
- 既存判定の隣接関係を維持する。

**Non-Goals:**
- 関数化やCLI構造の刷新、新しい依存関係の追加。
- 入力の再試行、EOFなど既存で未対応の例外の追加処理。

## Decisions

- `try` に対応する `else` 内で、15の倍数判定の後に独立した `if number > 0` / `elif number < 0` / `else` を置く。15の倍数用 `if` の内部に入れると非該当整数で表示されなくなるため、同じ深さに配置する。
- 既存結果の前や途中に挿入する案は、既存仕様の「直後の行」という契約に影響するため採用しない。追加表示は末尾とする。
- 文字列の先頭文字で符号を判断する案は採用せず、変換済み整数を比較する。これにより `-0` も0として扱い、既存の整数変換規則を維持する。
- テスト基盤の新設は行わず、実装時に標準入力を与えて標準出力を期待値と比較する。新規仕様の全シナリオと既存仕様の代表入力を確認する。

## Risks / Trade-offs

- [条件分岐の入れ子を誤ると一部入力で符号が表示されない] → 15の倍数と非倍数を正負の両方で確認する。
- [出力全体を比較する利用者の期待値が変わる] → 既存行は保持し、末尾の1行のみ追加する契約を差分仕様に明記する。
- [不正入力で未定義の変数を参照する] → 判定は整数変換成功時の `else` 内に限定し、不正入力3種で確認する。

## Migration Plan

実装後に代表入力の確認を完了してスクリプトを利用する。データ移行や依存関係の更新は不要。戻す場合は追加した符号判定ブロックを取り除く。
